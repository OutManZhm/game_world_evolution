# 世界演化系统现有数据模型清单

> 整理日期：2026-10-25  
> 依据：世界演化系统复刻设计文档 v0.3，第 5、6、8、10 章  
> 配套文件：[需求确认与填写表](世界演化系统需求确认与填写表.md)

## 1. 当前模型的范围

当前设计文档共定义 **34 张 SQLite 表**，涵盖世界实体、NPC 行动、人物关系、事件因果、环境调度和存档恢复。

这些是已经写入设计文档的表结构基线，不代表已经创建正式游戏数据库、完成 C# 实体或跑通世界模拟。下表列出各表的主键和主要字段；完整 SQL 以[主设计文档第 10 章](世界演化系统复刻设计文档.html#10)为准。

需要区分三种信息：

- **运行状态**：某个人在哪里、拥有什么、正在做什么，保存到 SQLite。
- **内容定义**：某种职业、行动、物品、灾害的规则，主文档计划由 JSON/YAML 配置，必要的版本与存档引用保存在 SQLite。
- **界面投影**：人物生平、编年史、事件卡等，由运行事实生成；目前没有为每种界面各建一张表。

## 2. 世界、地点与组织：5 张

| 表名 | 对应概念 | 主键 | 主要字段与用途 |
|---|---|---|---|
| `world` | 世界 | `id` | `seed`、`tick`、`pressure`、`config_version`、`state_json`；保存世界种子、当前回合、压力与扩展状态 |
| `region` | 区域 | `id` | `name_key`、`terrain`、`danger`、`owner_faction`；表示州、地区等大范围空间 |
| `locale` | 地点 | `id` | `region_id`、`kind`、`x/y`、`population`、`owner_faction`、`danger`、`state_json`；表示城镇、村落、门派驻地等 |
| `site` | 设施或资源点 | `id` | `locale_id`、`kind`、`owner_faction`、`resource_json`、`integrity`、`state_json`；表示农田、药铺、矿点等可经营或破坏对象 |
| `faction` | 组织或势力 | `id` | `kind`、`leader_id`、`headquarters`、`resources_json`、`goals_json`、`stance_json`；保存组织资源、目标与立场 |

空间结构为 `region → locale → site`。组织与地点是两个概念：一个组织可以控制多个地点，一个地点也可能存在多个组织的成员。

## 3. 人物、关系与认知：5 张

| 表名 | 对应概念 | 主键 | 主要字段与用途 |
|---|---|---|---|
| `npc` | 独立人物 | `id` | 身份：`name_key/sex/birth_tick/death_tick/faction_id/role_id/rank/office_id`；能力与权限：`authority/reach/ap_budget/location_id/health/realm/power`；扩展：`personality_json/needs_json/inventory_json/state_json` |
| `relation` | 人物有向关系 | `(from_id, to_id, kind)` | `affinity`、`trust`、`fear`、`debt`、`intimacy`、`last_contact`、`flags`；同一对人物可有多种关系 |
| `memory` | 人物对事件的记忆 | `(npc_id, event_id)` | `emotional_weight`、`source`、`created_tick`；记录事件给人物留下的情绪权重与来源 |
| `npc_belief` | 人物相信的事实版本 | `(npc_id, belief_key)` | `confidence`、`updated_tick`、`belief_json`；允许误会、错误传闻和不完整认知 |
| `knowledge_delivery` | 消息投递 | `id` | `source_event_id`、`sender_id`、`recipient_id`、`delivery_key`、`channel`、`sent_tick/deliver_tick`、`confidence`、`state`、`payload_json`；记录消息何时送达谁 |

`relation` 表达人物之间的关系，`memory` 表达人物记住了什么，`npc_belief` 表达人物目前相信什么，三者不能互相替代。`knowledge_delivery` 保存信息传播过程。

注意：`npc` 中的 `role_id`、`office_id` 等已经预留，但职业、职位的完整定义和任职历史尚未形成独立表。人物详细目标也没有独立的目标实例表，目前仅有行动计划中的目标引用与扩展载荷入口。

## 4. 回合、计划、行动与委派：7 张

| 表名 | 对应概念 | 主键 | 主要字段与用途 |
|---|---|---|---|
| `npc_turn` | 一个人的一回合 | `(npc_id, tick)` | `status`、`ap_budget/ap_spent`、`slots_used`、`time_budget/time_spent`、`trace_json`；证明该人物本回合有完整结算，保存选择原因与反馈 |
| `intent` | 已选择的行动意图 | `(npc_id, tick, seq)` | `kind`、`target_id`、`location_id`、`cost`、`directive_id`、`priority`、`score`、`state`；保存想做什么 |
| `action_plan` | 为目标制定的计划 | `id` | `npc_id`、`goal_id`、`revision`、`state`、`created_tick`；允许修订与跨回合执行 |
| `action_step` | 计划中的步骤 | `id` | `plan_id`、`kind`、`state`、`work_required`、`progress`、`definition_json`；保存持续行动的进度与执行规则 |
| `action_dependency` | 步骤依赖 | `(step_id, prerequisite_id)` | 指定哪些步骤成功后，当前步骤才可执行；禁止自依赖，完整无环性由业务校验保证 |
| `action_execution` | 实际行动尝试 | `id` | `step_id`、`npc_id`、`tick`、`slot`、`round`、`state`、`ap_spent/time_spent`、`reason`、`causes_json/results_json`；保存实际做了什么及成败 |
| `directive` | 委派命令 | `id` | `issuer_id`、`assignee_id`、`objective_json`、`priority`、`deadline_tick`、`depth`、`state`、`issued_tick`；支持接受、拒绝、执行、完成、失败与过期 |

典型关系：

```text
NPC 的目标引用
  → action_plan
  → action_step + action_dependency
  → intent
  → action_execution
  → 结果事件与效果账
  → npc_turn 汇总实际消耗、原因和下一回合待办
```

`intent` 是选择结果，`action_execution` 是实际执行记录。一个持续步骤可以在多个回合产生执行记录。回合表也能记录等待、休息、受伤无法行动等状态。

## 5. 事件、因果、张力与任务：7 张

| 表名 | 对应概念 | 主键 | 主要字段与用途 |
|---|---|---|---|
| `event_log` | 事件或事件计划节点 | `id` | `causal_seq`、`tick`、`type/layer/status`、`actor_ids/target_ids`、`location_id`、`root_id/parent_id/depth`、`decay`、`cause_ids`、`facts_json`、`visibility/salience/fingerprint` |
| `event_edge` | 实际因果关系 | `(from_event, to_event, kind)` | `weight`、`evidence_json`；保存直接引起、报复、揭露、传播、副作用、阻止等事实关系 |
| `event_template_edge` | 事件后继规则 | `(from_template, to_template, kind)` | `condition_json`、`bind_json`、`weight`、`max_fanout`、`cooldown_ticks`；定义满足条件后可能产生什么后继 |
| `tension` | 尚未解决的矛盾 | `id` | `type`、`subject_ids`、`stakes`、`urgency`、`deadline_tick`、`source_event`、`state`、`created_tick`；表示欠债、缺粮、职位空缺等局势 |
| `tension_cause` | 张力的多个来源 | `(tension_id, event_id)` | 保留同一矛盾的全部事件前因，避免合并张力时丢失原因 |
| `cascade_work` | 待处理的连锁工作 | `id` | `source_event_id`、`work_key`、`kind`、`due_tick/created_tick`、`priority/state`、`cursor_json/payload_json`；支持跨回合排队和分批扩展 |
| `contract` | 任务或契约 | `id` | `source_event`、`giver_id`、`objective_json`、`deadline_tick`、`reward_json`、`state`；把真实世界目标转为可参与任务 |

`event_edge` 是已经记录的事实关联，`event_template_edge` 是可能产生后继的规则。`root_id/parent_id` 只缓存一条主要叙事路径，多前因以 `event_edge` 为准。

## 6. 环境调度与效果：4 张

| 表名 | 对应概念 | 主键 | 主要字段与用途 |
|---|---|---|---|
| `event_schedule` | 定时调度 | `id` | `template_id`、`first_due_tick/next_due_tick`、`interval_ticks`、`repeat_limit`、`occurrence_index`、`state`、`policy_json`；保存一次性、周期或条件延期规则 |
| `environment_instance` | 某一次环境事件 | `id` | `schedule_id`、`occurrence_index`、`source_event_id`、`start_tick/end_tick_exclusive`、`state`、`scope_json/state_json`；区分每次旱灾、瘟疫等发生实例 |
| `environment_modifier` | 环境造成的临时修正 | `(instance_id, target_kind, target_id, effect_key)` | `value_fixed`、`stack_group`；保存某次事件对某个目标的产出、危险度等修正 |
| `effect_ledger` | 领域效果账 | `effect_id` | `source_event_id`、`tick`、`group_id`、`status`、`payload_json`；记录已应用或拒绝的变更，避免重复生效 |

典型关系：调度产生一次环境实例，实例产生临时修正和实际效果；临时修正在结束时移除，已经发生的资源损失、死亡或迁徙保留。

## 7. 存档、命令与恢复：6 张

| 表名 | 对应概念 | 主键 | 主要字段与用途 |
|---|---|---|---|
| `schema_migration` | 数据库结构版本 | `version` | `checksum`、`applied_at`；登记结构迁移 |
| `save_meta` | 存档元信息 | `key` | `value_json`；保存存档格式、游戏版本、内容版本等元数据 |
| `tick_commit` | 已提交回合 | `tick` | `previous_hash/state_hash`、`npc_count`、`command_cursor`、`rules_version`；标记完整回合及校验信息 |
| `command_log` | 外部输入命令 | `command_id` | `input_seq`、`target_tick`、`payload_json`；保存玩家等外部输入，支持回放和重复请求校验 |
| `tick_checkpoint` | 未提交回合的暂停检查点 | `id`，固定为 1 | `base_tick/base_hash`、`working_tick`、`rules_version`、`phase/round`、`cursor_json`、`payload/payload_hash`；恢复玩家交互暂停状态 |
| `world_snapshot` | 完整世界快照 | `tick` | `schema_version`、`rules_version`、`payload/payload_hash`、`state_hash`；保存同库快照以支持历史回放和恢复 |

数量核对：**5 + 5 + 7 + 7 + 4 + 6 = 34 张表。**

## 8. 已有概念，但模型仍需补充的部分

以下内容不能视为已经具备完整独立模型。可以后续建表，也可以定义严格的 JSON 结构，具体由规则和查询需求决定。

| 领域 | 当前已有入口 | 仍需要明确的信息 |
|---|---|---|
| 家庭与抚养 | 人物关系、`npc.state_json` | 家庭成员、共同财产、监护人、抚养责任、家庭消费 |
| 职业与岗位 | `npc.role_id/office_id`、地点与设施 | 职业定义、雇主、岗位容量、任职历史、工资、工时、失业与补缺 |
| 组织制度 | `faction`、身份字段、`directive` | 成员与职位关系、组织权限、任免、继任、财政与决策规则 |
| 财产权与账户 | 背包、组织资源、设施资源 | 所有者与管理者、公共/私人账户、仓库、转移记录、共有资产 |
| 资源与物品定义 | `resource_json/inventory_json` | 单位、分类、基础价格、腐坏、堆叠、生产配方、消耗规则 |
| 借贷与合同义务 | `relation.debt`、`contract` | 独立债权债务、币种、金额、到期、还款、违约、继承；不能用关系分数替代完整财务账 |
| 详细目标实例 | `action_plan.goal_id`、扩展载荷 | 目标定义与人物目标实例、触发来源、紧迫度、完成/放弃条件 |
| 道路与旅行 | 区域图概念、行动步骤进度 | 路线端点、距离、通行权、道路状态、在途位置与消息通路 |
| 行动时间与预约 | `time_budget/time_spent`、`action_execution` | 开始/结束时刻、资源占用、双人预约、同时发生时的仲裁 |
| 健康与疾病 | `npc.health/state_json`、生命周期规则 | 饥饿、伤势、疾病实例、传播、恢复、治疗与死亡条件 |
| 人口统计群体 | `Cohort` 概念、`locale.population` | 年龄结构、出生死亡迁移、与具名 NPC 的人口/劳动/消费去重 |
| 冲突与战争 | 事件、战力、组织立场 | 冲突实例、参战方、动员、补给、俘虏、占领、停战与条款 |
| 执法与裁决 | 信念、事件因果、任务 | 证据、案件、管辖权、调查、判罚、赔偿与和解 |
| 成长与传承 | 境界、战力、状态载荷 | 功法/技能定义、学习进度、突破材料、寿命变化、传授与遗失 |
| 长期世界更新 | 地点、设施、组织、事件 | 重建、组织成立/分裂/合并、产业兴衰、终局后的继续规则 |

## 9. 阅读和填写顺序

先填写[需求确认与填写表](世界演化系统需求确认与填写表.md)中的“第一轮关键选择”。这些选择确定模拟范围和玩法；随后才能准确决定哪些概念新增为表、哪些放进配置，以及每个字段的业务含义。

SQLite 的事务、幂等键、索引和迁移方式属于工程设计，不要求你填写 SQL 或决定每张表的技术结构。
